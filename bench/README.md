# Evidence Collector 계획 벤치마크

Evidence Collector가 **다음에 무엇을 조회할지 고르는 능력**만 떼어 재는 회귀
벤치마크입니다. 조사를 끝까지 실행하지 않고, 궤적 도중에 세워 다음 행동 하나를
예측하게 한 뒤 그 선택을 채점합니다.

설계는 [Agent Planning Benchmark (arXiv:2606.04874)][apb]를 따랐습니다. 그
논문의 관찰이 이 프로젝트에서 그대로 재현됐기 때문입니다 — 끝단 성공률만 보면
계획 실패와 실행 실패가 뒤섞여, 보고서가 틀렸을 때 **모델이 잘못 골랐는지 도구가
잘못 답했는지 구분할 수 없습니다.**

[apb]: https://arxiv.org/abs/2606.04874

## 왜 실행하지 않는가

조사를 실제로 돌리면 한 번에 수 분과 실제 토큰이 들고, 결과는 그때의 로그·
메트릭 상태에 따라 달라집니다. 같은 프롬프트가 어제는 통과하고 오늘은 실패할 수
있어 회귀 판정에 쓸 수 없습니다.

그래서 각 케이스는 **얼려 둔 궤적**입니다. 질문, 이미 호출된 도구, 그리고 그
도구들이 실제로 돌려줬던 응답까지 고정해 두고, 모델에게 다음 한 걸음만 묻습니다.
같은 입력이면 언제 돌려도 같은 판단을 요구할 수 있습니다.

## 채점은 규칙으로 한다

논문은 LLM-as-Judge로 계획의 질을 등급화합니다. 여기서는 그렇게 하지 않습니다.

**회귀 벤치마크의 케이스는 전부 이미 일어난 실패**이고, 실패마다 검사 가능한
서명이 있기 때문입니다. "`get_metric_history`에 배열을 넘겼는가"는 불리언이지 등급이
아닙니다. 판정자를 LLM으로 두면 채점 자체가 흔들려 회귀를 회귀로 못 읽습니다.

대신 논문의 **오류 분류(E1–E6)** 는 그대로 씁니다. 케이스마다 어느 유형을 막는
것인지 달아 두어, 실패가 나면 무엇이 무너졌는지 바로 읽힙니다.

| | |
|---|---|
| E1 | 목표 이해 오류 |
| E2 | 조기 종결 / 과제 미완결 |
| E3 | 제약 위반 |
| E4 | 논리 오류 |
| E5 | 도구 사용 오류 |
| E6 | 환각 |

## 케이스 종류

논문의 다섯 설정 중 이 시스템에 의미가 있는 넷을 씁니다.

- **step-wise** — 궤적 도중 다음 행동 예측. 대부분의 케이스가 여기 해당합니다.
- **tool-broken** — 도구가 오류를 돌려줬을 때 우회하는가, 데이터가 없다고
  결론짓는가. `get_mappings`가 실제로 고장 나 있어 실물 케이스가 됩니다.
- **tool-extraneous** — 라우터에서 뺀 Wazuh 도구 10개를 잡음으로 다시 넣어도
  옳은 것을 고르는가.
- **unsolvable** — 이 시스템이 볼 수 없는 것을 물었을 때 지어내지 않고
  `unknowns`로 남기는가.

논문의 holistic planning(전체 계획 일괄 생성)은 넣지 않았습니다. 이 Agent는
설계상 한 걸음씩 관측하며 좁혀 가므로 평가 대상이 아닙니다.

## 실행

```bash
cd ingress
OPENAI_API_KEY=sk-... npm run bench
```

키가 없으면 전부 건너뜁니다. `npm test`는 벤치마크를 포함하지 않으므로 CI와 일반
개발은 키 없이 그대로 돕니다.

특정 케이스만:

```bash
OPENAI_API_KEY=sk-... npm run bench -- -t "utc-is-not"
```

## 케이스를 추가할 때

**새 케이스는 실제로 일어난 실패에서만 만듭니다.** 있을 법한 실패를 상상해서
넣기 시작하면 사례집이 되고, 사례집은 프롬프트가 아니라 벤치마크에서도 같은
이유로 나쁩니다 — 통과해도 배운 것이 없습니다.

궤적의 도구 응답은 **그때 실제로 돌아온 문자열**을 씁니다. 요약하거나 다듬으면
모델이 실전에서 보는 것과 달라져, 통과가 아무것도 보장하지 않게 됩니다.
